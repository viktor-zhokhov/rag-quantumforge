# Задание 1. Исследование моделей и инфраструктуры

## 1. Контекст и ограничения

Заказчик — **QuantumForge Software** (Хельсинки + R&D в Таллине), SaaS «Digital Twin» для промышленного моделирования. Клиенты — ABB, Wärtsilä, скандинавские энергокомпании. Нужен внутренний RAG-бот по корпоративной базе знаний.

Прежде чем сравнивать инструменты, зафиксируем ограничения, которые задают рамки выбора. Именно они, а не «голая» производительность, определяют итоговое решение.

| Ограничение | Источник в кейсе | Следствие для выбора |
|---|---|---|
| **Юрисдикция ЕС (GDPR)** | HQ в Финляндии, R&D в Эстонии | Данные не должны бесконтрольно уходить в США; при облаке — только EU-регион и DPA |
| **Конфиденциальность** | «часть материалов не стоит уносить в облако» | Для чувствительных доменов нужен on-prem/локальный инференс |
| **SOC 2** | ~140 ч/год на сверку политик | Нужны трассируемость источников, аудит-логи, контроль хранения |
| **Объём и рост** | ~21 000 документов, +400 страниц/мес | Индекс должен переиндексироваться инкрементально и масштабироваться |
| **Существующий стек** | AWS (EKS+RDS), GitHub, Python/Go/Node | Развёртывание удобнее в Docker/K8s, экосистема Python |
| **Бюджет** | цель — снизить FTE-затраты на поиск | TCO (владение) важнее разовой цены |

Кто ставит задачу: руководство и GRC-команда (снижение затрат и подготовка к аудиту). Для кого делаем: разработчики, саппорт, менеджеры/аналитики, новые сотрудники.

> **Оценка объёма индекса.** ~21 000 документов при чанкинге в 500–1000 токенов дают порядка **150 000–300 000 чанков**. При 384-мерных эмбеддингах (float32 ≈ 1,5 КБ/вектор) это ~0,4–0,7 ГБ, при 1536-мерных (OpenAI) — ~1,8–3 ГБ. Вывод: индекс целиком помещается в RAM обычного сервера, экзотические распределённые хранилища на старте не нужны.

Все цены ниже — ориентировочные (середина 2025 г.), для сравнения порядков, а не для точной сметы.

## 2. Сравнение LLM: локальные (Hugging Face) vs облачные (OpenAI / YandexGPT)

| Критерий | Локальные (Llama 3.1 8B/70B, Mistral, Qwen2.5) | OpenAI (GPT-4o / 4o-mini) | YandexGPT |
|---|---|---|---|
| **Качество ответов** | 8B — средне; 70B — близко к GPT-4o на многих задачах, особенно после дообучения | Топовое, стабильное на сложных reasoning-задачах | Хорошее для русского; для англоязычной техдоки слабее GPT-4o |
| **Скорость** | Зависит от железа; на A100 8B — быстро, 70B — заметная задержка | Низкая латентность, но зависит от сети/лимитов API | Средняя, зависит от сети |
| **Стоимость** | Нет платы за токены; плата за GPU/электричество/DevOps | 4o ≈ $2.5/$10 за 1M вход/выход; 4o-mini ≈ $0.15/$0.6 | Оплата за токены в ₽ (по прайсу Yandex Cloud) |
| **Развёртывание** | Сложно: GPU, vLLM/TGI, обновления, мониторинг | Максимально просто: ключ + HTTP | Просто: API Yandex Cloud |
| **Данные / приватность** | Данные не покидают периметр — идеально для конфиденциального | Данные уходят в США (даже с opt-out нужен DPA) | Данные в РФ — для EU-компании юридически неудобно |
| **Vendor lock-in** | Нет | Есть | Есть |

**Вывод по LLM.** Для EU-компании с конфиденциальными данными оптимальна **двухконтурная схема**:
- **Локальная модель** (Llama 3.1 8B/70B через vLLM) — для чувствительных доменов, чтобы данные не покидали периметр.
- **Облачный GPT-4o-mini** (EU-регион, DPA) — для общих, неконфиденциальных запросов, где важна максимальная точность при низкой цене.

YandexGPT для финско-эстонской компании отпадает по юрисдикции (данные в РФ).

## 3. Сравнение моделей эмбеддингов: Sentence-Transformers vs OpenAI Embeddings

| Критерий | Локальные Sentence-Transformers (`all-MiniLM-L6-v2`, `bge-base`, multilingual) | OpenAI Embeddings (`text-embedding-3-small/large`) |
|---|---|---|
| **Скорость индексации** | На CPU — 5–10 мс/предложение; батчами на GPU — очень быстро; без сети | Ограничена сетью и rate-limit API; батч-запросы |
| **Качество поиска** | MiniLM (384) — хорошо для англ.; multilingual-модели покрывают EU-языки; bge-large — топ open-source | Высокое и стабильное; `3-large` (3072) — один из лидеров |
| **Стоимость** | Бесплатно (только вычисления) | `3-small` ≈ $0.02/1M токенов, `3-large` ≈ $0.13/1M |
| **Приватность** | Тексты не покидают периметр | Весь корпус уходит в API при индексации ← критично |
| **Размер вектора** | 384–1024 (компактный индекс, дешевле хранить) | 1536–3072 (больше RAM/диск) |

**Ключевой довод:** при индексации через облако **весь корпус базы знаний уходит на сторонний сервис** — а он содержит конфиденциальные материалы. Это прямо конфликтует с ограничением кейса.

**Вывод по эмбеддингам.** Берём **локальные Sentence-Transformers**. Для многоязычной EU-документации — `paraphrase-multilingual-MiniLM-L12-v2` или `bge-m3`; для англоязычного ядра — `all-MiniLM-L6-v2` (быстро, 384-мерно, компактный индекс). Эмбеддинги считаются локально → конфиденциальность соблюдена, платы за токены нет, индексацию легко пересобирать при росте +400 страниц/мес.

## 4. Сравнение векторных БД: FAISS vs ChromaDB

_(с оглядкой на Qdrant/Pinecone как варианты для продакшена)_

| Критерий | **FAISS** | **ChromaDB** | Qdrant (для справки) |
|---|---|---|---|
| **Скорость поиска/индексации** | Очень высокая, in-process C++ (IVF/HNSW/PQ) | Высокая in-process, но упирается в RAM | Высокая (Rust), дисковый HNSW |
| **Метаданные / фильтрация** | Нет «из коробки»; фильтр — вручную (маски, внешние id) | Есть простые and/or-фильтры + произвольный JSON | Богатая фильтрация, geo, типизированный payload |
| **Хранение метаданных** | Нет — нужно внешнее хранилище | Хранит рядом с вектором | Хранит рядом с вектором |
| **Сложность внедрения** | Минимальная: `pip install faiss-cpu`, 5 строк | Низкая, «Pythonic», нативная интеграция с LangChain | Средняя: `docker run qdrant/qdrant` |
| **Персистентность** | Файлы индекса вручную (save/load, бэкап) | Встроенная (SQLite/DuckDB) | Полноценная БД, снапшоты, репликация |
| **Масштаб** | Миллионы векторов в RAM; десятки млн — ухищрения | До ~10 млн, ограничен RAM | Сотни млн, шардинг, кластер |
| **Стоимость владения** | Бесплатно, только вычисления | Бесплатно, только вычисления | Бесплатно self-host / платный Cloud |
| **Развёртывание** | Внутри процесса бота (нет отдельного сервиса) | Внутри процесса или отдельный сервер | Отдельный сервис (Docker/K8s) |

**Разбор под наш кейс.**

- Объём (150–300k чанков) целиком влезает в RAM → распределённое хранилище на старте избыточно.
- FAISS даёт максимальную скорость и простоту, полностью локален (конфиденциальность), не тянет внешних сервисов — идеален для MVP и для research-фазы этого проекта.
- Слабое место FAISS — **фильтрация по метаданным** (язык, версия документа, роль пользователя, свежесть). А кейсу это нужно: многоверсионная документация, RBAC-доступ (юрист/инженер видят разное), фильтр по актуальности.
- Chroma закрывает метаданные и персистентность «из коробки», но по скорости/масштабу проигрывает и в проде всё равно упрётся в RAM.
- Qdrant (self-hosted, on-prem в EU) — правильная цель для продакшена: богатая фильтрация, RBAC-сценарии, снапшоты для SOC 2, горизонтальное масштабирование под рост.

**Вывод по векторной БД.**
- **Для MVP / этой проектной работы — FAISS**: локально, бесплатно, быстро, минимум инфраструктуры; метаданные храним рядом (в `.json`/`.pkl`) и фильтруем постобработкой.
- **Документированный путь миграции в Qdrant (self-hosted, EU)** для продакшена, когда критичными станут фильтрация по метаданным, RBAC и масштаб. API RAG-пайплайна проектируем так, чтобы смена хранилища не затрагивала остальную логику.

## 5. Конфигурация сервера

Требования по компонентам:

| Компонент | Ресурс | Комментарий |
|---|---|---|
| Эмбеддинги (Sentence-Transformers) | CPU достаточно; GPU ускоряет батч-индексацию | MiniLM отлично работает на CPU |
| FAISS-индекс | RAM (0,5–3 ГБ) + CPU | Целиком в памяти |
| Локальная LLM 8B | GPU 16–24 ГБ VRAM (напр. RTX 4090 / A10) | С квантованием (4-bit) влезает в 24 ГБ |
| Локальная LLM 70B | 2×A100 40/80 ГБ или квантование на 48 ГБ | Дорого; только если нужен максимум качества on-prem |
| Оркестрация | Docker / EKS (уже есть у компании) | Вписывается в текущий стек |

## 7. Рекомендация

**Выбираем Вариант D (гибрид) с векторной БД FAISS для MVP:**

- **Векторная БД — FAISS.** Локальна (конфиденциальность), бесплатна, максимально быстра, минимум инфраструктуры, отлично подходит для research-фазы и MVP. Метаданные (источник, версия, роль, дата) храним рядом с индексом и применяем постфильтрацией. Заложен путь миграции в **Qdrant self-hosted (EU-регион)** для продакшена под фильтрацию, RBAC и масштаб.
- **Эмбеддинги — локальные Sentence-Transformers** (`all-MiniLM-L6-v2` для англ. ядра, multilingual-модель для остальных языков): весь корпус остаётся в периметре, платы за токены нет, лёгкая переиндексация под рост.
- **LLM — двухконтурная:** облачный GPT-4o-mini (EU, DPA) для общих запросов + локальная Llama 3.1 8B для конфиденциальных доменов.
- **Сервер:** для MVP — узел с CPU (8+ ядер) и 16–32 ГБ RAM для эмбеддингов и FAISS; при подключении локальной LLM — GPU 24 ГБ (RTX 4090 / A10). Развёртывание в Docker, далее в существующий EKS.

**Почему так:** решение уважает ключевые ограничения кейса (GDPR, конфиденциальность, SOC 2), минимизирует TCO, просто стартует и имеет ясный путь роста без переписывания RAG-пайплайна.

> Для целей проектной работы (Задания 2–5) используется именно **FAISS** — как заявлено в этой рекомендации.
